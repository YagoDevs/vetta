# vetta.

**Agentic triage for data-science take-home assessments — with claims verified by execution, not by reading.**

Built for the micro1 Agentic Workflows Hackathon (Aug 28-31, 2026).

## The user and the bottleneck

A tech recruiter (or hiring manager) sends a data-science case to candidates and gets back
a pile of Jupyter notebooks. Today, a senior data scientist spends 30-60 minutes per
notebook: running it, checking whether the metrics in the write-up match what the code
actually produces, hunting for data leakage, judging the conclusions. With 20 candidates
that is a week of expensive, inconsistent work — and it is the actual bottleneck between
"assessments received" and "shortlist delivered".

The dangerous part: **a notebook can look great and be wrong in ways reading cannot catch.**
A claimed AUC that no cell reproduces. A result that changes every run because no seed was
fixed. A cell that only worked because of stale kernel state. Static review — human or LLM —
is blind to all of it.

## The thesis (and the hot take)

> There is a class of defects in analytical work that only *execution* reveals.
> An agent that re-runs the notebook and diffs *what was claimed* against *what actually
> happens* catches them; a single strong LLM prompt reading the executed notebook does not.

We pre-registered that claim, built both systems, and measured it.

## What vetta does

```
folder of candidate notebooks
        │
   [1] Executor      – runs each notebook twice (sandboxed, no LLM): real metrics,
        │              broken cells, seed sensitivity. Facts only.
   [2] Verifier      – LLM agent: diffs candidate claims against executed facts.
        │              Every finding cites the exact cell + executed evidence.
   [3] Assessor      – LLM agent: scores the pre-registered rubric with verified
        │              findings on the table (judging separated from hunting).
   [4] Reporter      – deterministic decision rules + one LLM call for the
        │              recruiter-readable summary.
        ▼
 results/*.json  →  dashboard (ranked queue · cell-level evidence · human decision)
```

The LLM never produces a fact — it interprets and judges facts the Executor produced.
The final decision is always human: the dashboard records the recruiter's own
advance/review/reject with a note (hackathon ground rules 04/05).

## Measured improvement

Baseline (deliberately strong, not a strawman): the **same model, same rubric, same defect
taxonomy**, single prompt, given the notebook **with its executed outputs included**. The
only thing it lacks is vetta's process: independent re-execution, claim-vs-reality diffing,
dual-run seed check.

Test set: 8 synthetic candidate notebooks generated by `scripts/build_notebooks.py` from a
real telecom-churn case, with **12 planted defects** registered at injection time in
`ground_truth/defects.json` (objective, cell-level ground truth — anyone can open the cell
and check). Three independent runs of each system (`official_a/b/c`), mean reported:

| Metric (mean of 3 runs)              | Baseline | vetta | Δ |
|--------------------------------------|---------:|------:|---|
| Defect detection F1                  | 0.763    | **0.853** | +0.09 |
| Defect precision                     | 0.725    | **0.822** | +0.10 |
| Defect recall                        | 0.805    | **0.889** | +0.08 |
| Recall — static defects (S1-S4)      | **1.000**| 0.800 | −0.20 |
| Recall — execution-only defects (E1-E4) | 0.667 | **0.952** | +0.29 |
| Decision accuracy                    | **0.958**| 0.875 | −0.08 |

**The result matches the pre-registered thesis with unusual precision.** The entire
advantage concentrates in execution-only defects (+0.29 recall) — inflated metrics,
seed-dependent results, broken cells, orphan conclusions. And the honest flip side:
the baseline *reads* better than our verifier (static recall 1.0 vs 0.8) and its
harsher instincts score slightly better on the 3-way decision. Verification wins
exactly where verification is possible; it does not dominate everywhere. That is the
main lesson — see the changelog.

## Improvement changelog

| Stage | What we tried and why | Evidence (same eval, 8 notebooks) | Decision / learning |
|---|---|---|---|
| Baseline | Single strong prompt, executed notebook included | F1 0.71-0.80, misses inflated metrics & seed instability; approved a candidate whose result changes every run | Established: static reading has a blind spot — the thesis target |
| Pipeline v1 | Executor→Verifier→Assessor→Reporter | Caught E1 with exact cell evidence, but flagged S3 on clean notebooks (printing accuracy ≠ celebrating it) | Verifier taxonomy needed sharper S3 definition |
| Iteration 1 | S3 restricted to *narrative* reliance on misleading metric | Clean notebooks still flagged — and the verifier was RIGHT: our "gold" notebook overclaimed (conclusions without a supporting cell) | Kept — and fixed the gold notebook instead of weakening the verifier. Lesson: a good verifier audits your own test set |
| Iteration 2 | Explicit finding→criterion map in the Assessor (an S3 must not tank C3) | Decision accuracy 8/8, clean notebooks 0 false positives | Kept — separating hunting (verifier) from judging (assessor) only works if the mapping is explicit |
| Iteration 3 | S4 detection hint (coerce+dropna pattern), one-finding-per-claim dedup, E1 gap threshold | Recall 1.0 both classes, but new pedantic FPs (coefficient interpretation, acknowledged limitations) | Revised — over-instructing creates zeal; every hunting hint needs its negative case |
| Iteration 4 (frozen) | Seedless special-case (drift→E3 only, not E1/E4), acknowledged-limitation exemption for S3 | Official runs: F1 0.853±0.02 vs baseline 0.763±0.04 | Final system |
| Removed | Ranking correlation (Spearman vs author ranking) as primary metric | — | Dropped before implementation: N=8 ranking is noise and author-judged ranking is circular. Replaced by per-defect precision/recall against injection-time ground truth |

**Main failure mode:** the verifier consistently misses one S4 (silent data loss) that the
baseline catches by reading — our execution-focused prompt under-weights purely static
inspection. **Hot take:** giving an agent tools changes what it looks for; our verifier
"trusts" execution so much it reads less carefully than a model that can *only* read.
A production system should run both lenses and merge findings — active verification is
a complement to static review, not a replacement.

## Reproduce it

See [REPRODUCE.md](REPRODUCE.md). Short version:

```bash
make setup        # venv + pinned deps (python 3.12+)
make reproduce    # OFFLINE replay of the 3 official runs — no API key, no cost, ~2 min
make serve        # dashboard at http://localhost:8000
```

`make rerun` repeats everything live with your own `OPENAI_API_KEY` (~US$2, ~20 min).
Model pinned to the dated snapshot `gpt-5.2-2025-12-11`.

## What existed before vs. what we built

Pre-existing: OpenAI API + SDK, papermill/nbclient, FastAPI, React/Vite/Tailwind, and a
telecom-churn case previously solved by the author (inspiration for the synthetic data
generator). Everything else — pipeline, agents' instructions, defect taxonomy, rubric,
notebook/defect injection scripts, evaluation harness, replay infrastructure, dashboard —
was built during the hackathon. AI review platforms (CodeSubmit, HackerRank AI review)
score submissions by static analysis; none we found executes and diffs claims.

## Agent trajectories

Committed per candidate inside each verdict (`results/official_*/nb*.json`, `trajectory`
field) and browsable in the dashboard ("O que o agente fez" tab): executor facts →
verifier findings → assessor scores, plus every raw LLM call in `runs/official_*/calls/`.
